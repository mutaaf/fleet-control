## User story

As a fleet operator away from my laptop, I want a phone push when the
fleet hits a self-cancel, an open PR sits >2h with green CI, or an anomaly
fires, so that I can intervene without checking the portal proactively.

## Why now (four lenses)

### Product Owner
The local daemon already does osascript alerts (P7 in the existing
build); they're useless when the operator isn't at the desk. ntfy.sh is
free, anonymous, and HTTP-only — perfect for this.

### Stakeholder
Widens the moat on `observability`. Pairs with anomaly detection (0008)
and budget caps (agent-fleet 0004).

### Operator
Phone buzzes: "almanac: PR #82 sat 2h with green CI — tap to approve."

### Growth
The kit becomes operable from anywhere, on any device, with zero infra.

## Acceptance criteria

- [ ] `src/alerts.ts` gains an exported `sendNtfy(topic, payload)`
      function that uses `https.request` (`node:https`) to POST a JSON
      body `{title, message, priority, tags, click, actions?}` to
      `https://ntfy.sh/<topic>`. Returns `{ok: boolean, status, error?}`
      — never throws. Request times out after 5s.
- [ ] Topic comes from a new field in `fleet-control.config.json`:
      `ntfyTopic` (string). If unset or empty, `sendNtfy` is a no-op that
      returns `{ok: true, status: 0, error: "disabled"}` — osascript
      stays the only channel. Test: omit field, call sendNtfy, assert no
      socket attempt.
- [ ] `src/alerts.ts` ntfy dispatch fires on the existing `alert` rows
      already generated by the rule engine, gated by severity:
      `critical` → ntfy priority 5, `warn` → priority 3. Same dedup
      key as osascript — one notification per (dedup_key) lifetime, not
      one per tick. Test: insert the same alert twice, assert one POST.
- [ ] Additionally, fires when an `anomaly` row is inserted (ticket
      0008). If ticket 0008 hasn't shipped, the dispatch is a no-op
      because no rows exist — does not break.
- [ ] The `click` URL points at the operator's portal. Default
      `http://127.0.0.1:7070/#/p/<slug>` (matches the existing SPA hash
      route); configurable via `portalUrl` in `fleet-control.config.json`.
- [ ] Best-effort: HTTP failure (non-2xx, timeout, DNS) logs to
      `~/.local/state/fleet-control/logs/fleetd.err` with a one-line
      `ntfy error: <status>` and continues. The daemon never crashes
      because ntfy is down. Test: stub https.request to call back with
      an error, assert `sendNtfy` returns `{ok: false}` and the caller
      proceeds.
- [ ] `bin/fleetctl.ts ntfy test` POSTs a test message to verify the
      operator's setup. Exit 0 on success, 1 on failure with a printed
      reason. Test: stub https, assert exit code path.
- [ ] `tests/ntfy.test.ts` covers the cases above by stubbing
      `node:https` (inject the request factory via a module-local
      `setHttps()` for testability — no monkey-patching globals).
- [ ] No new runtime deps. `tsc --noEmit` clean. No shell-string
      composition.

## Out of scope

- Per-rule topics. One topic for all rules in v1.
- Authenticated ntfy. Free public topics only.
- iOS-specific actions. Plain notifications.

## Engineering notes

- `src/alerts.ts` — extend the existing alert dispatch.

- `fleet-control.config.json` — add `ntfyTopic`, `portalUrl`.
