## User story

As a fleet operator who wants to show a friend "look what my agents
shipped last month" without granting them portal access, I want a
single stable public URL like `/receipts/<slug>/<YYYY-MM>` that
renders one tweet-shaped page - "May 2026: 47 PRs merged, $8.42
total spend, $0.18 per merged PR, 6/30 ship-days red, top mover
courtiq +12 PRs" - so that I can paste it into a DM and the
recipient sees the artifact without auth, without my admin token,
without my project list, and decides on the spot whether they want
their own fleet-control.

## Why now (four lenses)

### Product Owner
0013 (shareable snapshot) already exists, but it is a portal MIRROR -
a logged-in-style dashboard frozen for a viewer with a secret URL.
It is designed for "show this exact state to someone I trust,"
not for "show a prospective adopter the marketing-shaped headline."
The receipts page is the OPPOSITE shape: ONE month, ONE project (or
ONE fleet-wide aggregate), four stats, one headline, no controls,
no project list, no inline cost charts beyond the headline number.
Crucially: the URL pattern is PREDICTABLE (`/receipts/<slug>/<month>`),
not a secret token, because the operator wants to be able to TWEET it
and have it indexed - the privacy gate is that ONLY months the
operator has explicitly published render; everything else returns 404.
Pure composition over the existing `cost_rollup_day` + `pr` tables
the digest (0012) and cost-per-PR (0035) already use, plus a new
tiny `receipts_published` table that whitelists `(project_slug,
month_iso)` tuples - if the row exists, the page renders; if not,
404. The publish action is a single CLI subcommand
(`fleetctl receipts publish <slug> <month>`) and a one-tap portal
button on the existing 0012 digest page.

### Stakeholder
Widens the moat on the acquisition axis specifically. 0013 snapshot
is a TRUST artifact (one operator showing another a specific
moment). 0032 welcome QR is an ONBOARDING artifact (one operator
pairing their own phone). 0025 demo sandbox is a TRY-IT artifact
(a prospective operator booting the demo). Receipts are a
PROSPECTING artifact: the operator posts it once, anyone with the
link sees it forever, the page itself terminates with
`<a href="https://github.com/mutaaf/fleet-control">get fleet-control</a>`.
That is the single artifact in the fleet-control surface that a
NON-USER sees voluntarily and converts on - the screenshot worth
sharing, in literal URL form. Per the cross-fleet courtiq lesson
"a share-worthy artifact answers the question 'why this tool?'
better than a landing page," the receipts URL IS the landing page
for the operator's chosen month.

### User (operator at 9am, deciding whether to share)
On the existing weekly digest (0012) and the 0036 cross-fleet
lessons page, a single "Publish May receipts" button appears next
to the monthly summary. Tapping it: shows a preview of the rendered
page in a modal, lists what the public will see ("47 PRs, $8.42,
$0.18/PR" - no project names of OTHER projects, no PR titles, no
costs broken down by phase), asks "publish to a public URL?"
Confirming: the next page render shows "Published. URL:
fleet-control.local/receipts/courtiq/2026-05 [copy] [tweet this]".
The operator can UNPUBLISH at any time via the same modal (deletes
the row, the URL 404s immediately). The receipts page itself, when
fetched by a stranger, is a SINGLE column of four stats in big type,
one project name, one month label, one footer line "Generated by
fleet-control on 2026-06-01 - get yours at <github url>." No
JavaScript - server-rendered HTML, so it works on a flaky cellular
connection AND can be screenshot-shared with the URL bar showing.
At 375px viewport the page is still readable - the four stats stack
vertically.

### Growth
The screenshot worth sharing is THE URL ITSELF: pasted into a
group chat, the rendered preview unfolds and the recipient sees
"$0.18 per merged PR, 47 shipped" without clicking. That is the
"show me" moment - a stranger-readable artifact tied to a stable
URL that the operator can curate (only published months exist).
0013 snapshot is private-by-default (token in URL); receipts are
public-by-explicit-action. The two are distinct shapes serving
distinct audiences: snapshot = trusted reviewer at the moment of
question, receipts = anonymous strangers being recruited. Per the
cross-fleet courtiq lesson "a public artifact is the cheapest
acquisition surface" the receipts URL is the first thing a
prospective operator ever sees - before they ever clone the repo,
before they ever run `fleetctl demo`, the receipts URL their friend
sent them is the pitch.

## Acceptance criteria

Each box maps 1:1 to a test scenario. PRODUCER-VS-SPEC NOTE: when
this spec names a column value literally (`pr.state = 'MERGED'`,
`outcome = 'shipped'`, etc.), the implementing dev MUST grep
`src/ingest/prs.ts` and `src/ingest/runs.ts` for the producer's
actual casing before writing the SELECT. Per LESSONS 2026-06-05
"groomer prose can disagree with the schema; the schema wins":
the schema is the contract, this spec is a hint. The ingester
writes `pr.state = 'open'` lowercase for open PRs (line 164 of
prs.ts) and other views (`src/views.ts:706`, `:2213`) use
`state = 'MERGED'` upper-case for merged PRs - the receipts helper
matches whatever the existing producers / fellow views use.

- [ ] New schema: `CREATE TABLE IF NOT EXISTS receipts_published
      (project_slug TEXT NOT NULL, month_iso TEXT NOT NULL,
      published_at TEXT NOT NULL, payload_json TEXT NOT NULL,
      PRIMARY KEY (project_slug, month_iso))` added under the
      existing schema block in `src/db.ts`. The `payload_json`
      column carries a FROZEN snapshot of the four stats taken at
      publish time, so the URL remains stable even if the
      underlying runs are later deleted by the stale-checkout
      janitor (0006). Per LESSONS § "no backticks inside template-
      literal SQL strings", identifiers stay plain words inside
      the SCHEMA template. Test: open a fresh DB, assert the table
      exists with the right columns; open a DB that already has
      the table, assert no error (idempotent).
- [ ] `src/views.ts` exports `receiptsFor(db, projectSlug:
      string | "fleet", monthIso: string, now: Date): {found:
      boolean, project_slug: string, project_label: string,
      month_iso: string, month_label: string, merged_prs: number,
      total_spend_usd: number, cost_per_pr_usd: number | null,
      red_days: number, top_mover: {slug: string, delta_prs:
      number} | null, generated_at: string} | null`. When the
      requested `(project_slug, month_iso)` has NO row in
      `receipts_published`, returns `null` (the route translates
      that to 404). When the row IS present, returns the FROZEN
      `payload_json` parsed - never re-derives from runs at read
      time, so a published artifact is immutable. The
      `project_slug === "fleet"` form aggregates across every
      project the operator has published a fleet-wide entry for.
      Per LESSONS § "node:sqlite's .all() needs `as unknown as
      T[]`", every row narrowing uses the double-cast. Test: seed
      a published row, assert the four stats match the frozen
      payload; query an unpublished month, assert `null`; query
      after deletion, assert `null` next call.
- [ ] `src/views.ts` exports `computeReceipts(db, projectSlug:
      string | "fleet", monthIso: string, now: Date): <same shape,
      always non-null with found:true>`. This is the COMPUTE path
      called at publish time. Walks `cost_rollup_day` for spend,
      `pr WHERE state = <merged-casing>` for merged_prs and per-
      day red breakdown, then derives `cost_per_pr_usd =
      total_spend_usd / merged_prs` (null when `merged_prs === 0`),
      `red_days` = count of distinct dates in the month where the
      project had at least one open PR with `ci_state` matching
      the producer's failing token (grep `src/ingest/prs.ts` for
      the actual ciState() return surface before writing - the
      schema wins per LESSONS 2026-06-05), and `top_mover`
      (fleet-wide receipts only) = the project with the largest
      month-over-month delta in `merged_prs`. Per LESSONS §
      "julianday() drifts ~10us per timestamp", any per-day
      date diff uses strftime decomposition. Test: seed runs
      across May for a known project, call `computeReceipts`,
      assert each of the four stats to the exact number.
- [ ] `POST /api/receipts/publish` body `{project_slug, month_iso,
      payload?}` requires `admin` scope. Computes receipts via
      `computeReceipts`, persists the frozen payload via INSERT
      OR REPLACE on `receipts_published`. Returns
      `{published_url: string, payload: <shape>}`. Validates
      `project_slug` against the existing `project` table (or
      the literal `"fleet"`) and `month_iso` against
      `/^\d{4}-(0[1-9]|1[0-2])$/`; both must pass before the row
      is written. Test: hit without `admin` scope -> 403; with
      a valid slug/month -> 200 with `published_url` matching
      `/receipts/<slug>/<month>`; with an unknown slug -> 400;
      with a malformed `month_iso` -> 400.
- [ ] `POST /api/receipts/unpublish` body `{project_slug,
      month_iso}` requires `admin` scope. Deletes the row. Returns
      `{ok: true}` even when the row was already absent
      (idempotent). Test: publish then unpublish, assert the next
      GET returns 404; unpublish an absent row, assert 200.
- [ ] `GET /receipts/<slug>/<YYYY-MM>` is unauthenticated and
      mounted in the SAME outer handler as the existing
      `/share/<token>` route (per `src/server.ts:1265`). Returns
      200 with `content-type: text/html; charset=utf-8` when a
      published row exists, 404 otherwise. The page is
      server-rendered single-column HTML, NO `<script>` tag, NO
      reference to `/api/control/`, NO list of projects other
      than the one published, NO PR titles, NO admin token leak,
      NO github.com anchor pointing at the operator's repo (the
      only github anchor is `<a
      href="https://github.com/mutaaf/fleet-control">get
      fleet-control</a>` in the footer). Per LESSONS §
      "defence-in-depth secret redaction at the renderer
      boundary", every operator-visible string passes through
      `redactSecrets` before insertion. Per the existing 0013
      `serveShare()` pattern, the helper lives in a new
      `src/receipts.ts` module exposing `serveReceipts(db, slug,
      month): {status, headers, body}`. Test: fetch a published
      URL, assert 200 + text/html + the four stats are present
      in the body; assert NO `<script>` tag, NO
      `/api/control/`, NO admin token substring, NO github.com
      anchor other than the fleet-control footer; fetch an
      unpublished URL, assert 404.
- [ ] Caching: `GET /receipts/<slug>/<YYYY-MM>` sets
      `Cache-Control: public, max-age=600` (10 min - the payload
      is immutable but the operator may unpublish; 10 min
      balances CDN reuse against the unpublish UX). The handler
      memoises by `(slug, month_iso)`. Per LESSONS §
      "in-process dedup sets need an explicit reset hook for
      tests", expose `_resetReceiptsCacheForTests()` AND
      `_getReceiptsCacheBuildsForTests()` per LESSONS §
      "expose a build counter for cache-hit tests, not a
      fetcher swap". Test: two fetches within 10 min assert the
      build counter increments once; an unpublish-then-fetch
      assert the build counter does NOT increment (the cache
      now returns the stale page until eviction OR explicit
      invalidation - assert the unpublish handler invalidates
      the cache key for that slug/month).
- [ ] Portal publish UI: the existing weekly digest (0012)
      surface grows a "Publish receipts" button next to each
      month's row. Tapping it opens a modal that PREVIEWS the
      rendered page in an `<iframe>` of the receipts URL with
      `sandbox="allow-same-origin"` (no scripts), lists the
      fields that will be public, and requires a confirm tap
      before POSTing to `/api/receipts/publish`. After publish,
      the button text becomes "Unpublish" and the row shows
      the stable URL + a "copy" button. On phone the modal
      fills the viewport. Per LESSONS §
      "defence-in-depth secret redaction at the renderer
      boundary", the preview iframe's URL is the same public
      URL anyone else would fetch - the preview cannot leak
      private fields the public page would hide. Test: stub
      the API, tap publish, assert the POST shape; tap
      unpublish, assert the DELETE shape and the URL row
      disappears.
- [ ] `fleetctl receipts <subcommand>` CLI: `publish <slug>
      <month>`, `unpublish <slug> <month>`, `list` (one row
      per published `(slug, month)` with the public URL).
      The CLI shells the same admin-scope HTTP path internally
      via the localhost server when running, OR writes the
      `receipts_published` row directly when invoked offline
      (subcommand auto-detects via `lsof -iTCP:<port>`). Per
      LESSONS § "CLI subprocess tests need a `FLEET_DB_PATH`
      env seam", tests drive the offline path with
      `FLEET_DB_PATH=<tmp>` and the running path with a stub
      server. Per LESSONS § "shell-out modules need an
      injectable runner for tests", any shell-out (the
      `lsof` probe) goes through the existing
      `_setRunnerForTests` seam. Test: subprocess-spawn the
      CLI, publish a month, assert the row exists; list,
      assert it appears; unpublish, assert it disappears.
- [ ] Mobile: at 375px viewport the receipts page stacks the
      four stats vertically in a single column with the
      headline number at minimum 36px font-size; the project
      name and month label sit above the stats; the footer
      "get fleet-control" link sits below. NO horizontal
      scroll (per the 0011 mobile-portal contract). At
      >=600px the four stats sit in a 2x2 grid. Test: assert
      via the existing mobile-portal text-level CSS
      contract at 375px and 600px - count the visible nodes,
      assert no overflow.
- [ ] Quiet-hours integration: the publish action does NOT
      check quiet hours (publishing is operator-initiated,
      not an alert). The receipts page itself does NOT
      surface any alert text the operator's quiet-hours
      window would suppress on the live portal. Test: stub
      quiet hours active, publish, assert the row is written;
      stub quiet hours active, fetch the public URL, assert
      the page renders normally.
- [ ] No new runtime deps. `tsc --noEmit` clean. No
      shell-string composition - every `execFile` uses argv
      arrays. No JSON-shape break to any existing `/api/...`
      route - the new `/api/receipts/{publish,unpublish}`
      routes are net-new; the digest payload (0012) is
      unchanged (the publish button reads its existence from
      a separate `/api/receipts/published?slug=&month=` HEAD

      (`receipts_published`) added to the existing SCHEMA
      block in `src/db.ts`. Per LESSONS § "no backticks

      server-boot tests plant a tmp
      `fleet-control.config.json` in cwd and restore on

## Out of scope

- A LEADERBOARD across multiple operators ("fleet-control
  users ranked by PRs/month"). v1 is purely the single
  operator's published artifact - no cross-operator
  comparison surface, no centralised aggregator. That
  surface is a separate product.
- Inline PNG generation (e.g. og:image for rich-link
  previews). The HTML page is enough for v1; PNG
  generation needs a Cairo/Canvas dep and breaks
  zero-runtime-deps. The og:image meta tag points at the
  HTML preview itself (browsers degrade gracefully).
- Per-day or per-week receipts. v1 is MONTH only - the
  unit of mind for "look what shipped" is a calendar
  month. Weekly receipts would race the existing 0037
  Friday wrap card.
- A receipts-page-level "subscribe to my future receipts"
  RSS / email feed. The operator posts the URL when they
  want to; no inbound list mechanic.
- Receipts for FAILED projects ("my project shipped 0 PRs
  last month, here's why"). The receipts shape is a
  CELEBRATION artifact; failure narratives are a
  different surface (the 0008 anomaly digest).
- Auto-publish on the 1st of the month. Publishing is
  operator-initiated by design (it is a public action).
  An auto-publish toggle in a future ticket is fine; v1
  is opt-in per month.
- An UNPUBLISHED preview URL (a private-token preview).
  The portal's publish modal already previews the page
  via an iframe of the PUBLIC URL - a separate
  private-token preview would re-implement the 0013
  snapshot shape and confuse the two artifacts.
- Per-project custom theming / colours. v1 is one
  layout, one font stack (system stack), one neutral
  colour. Theming is a follow-up if requested.
